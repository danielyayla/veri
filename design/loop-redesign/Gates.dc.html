Retry queue lives in Postgres, not SQS
Surfaced while implementing WO-165 · constrains REQ-036
FLAGGED BY THE AGENT — READ THESE FIRST
At-least-once delivery strains [[REQ-036]]'s no-duplicate-reminder constraint — the dedupe key on (invoice_id, kind) must be in the same migration or the constraint is briefly false.
Polling the queue table adds vacuum pressure on the busiest database — needs the fill-factor tweak from the ops runbook, owner: platform.
ALTERNATIVES THAT COULD HAVE BEEN CHOSEN
SQS with a dead-letter queue rejected
New infrastructure for one queue; local development loses parity with production. Revisit if a second queue consumer appears.
In-process retry with backoff rejected
Loses queued retries on restart — fails REQ-036's guarantee that an overdue invoice is never silently skipped.
REVISIT WHEN
Queue depth sustains above 10k, or a second consumer needs the queue. Either condition arriving surfaces this decision back at your gate.
