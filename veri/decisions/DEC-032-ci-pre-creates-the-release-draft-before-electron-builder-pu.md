## Choice

electron-builder never touches the release API. The release workflow
creates the draft release itself (`gh release create --draft
--verify-tag`) before packaging, electron-builder runs with
`--publish never` (which still writes the DMG, zip, both blockmaps,
and latest-mac.yml into its output directory — verified locally on
0.1.2), and CI uploads those five files to the draft in one serial
`gh release upload`. After uploading, the job asserts via GraphQL
that the tag has exactly one release carrying the full asset set and
fails otherwise.

Evidence forcing this shape (2026-08-17): electron-builder's DMG and
zip publishers run concurrently, and each does its own
list-then-create against GitHub's REST list-releases endpoint. On
the v0.1.1 run the two creates raced (classic check-then-act),
splitting assets across two drafts. On the v0.1.2 run a pre-created
draft did not help: the REST list endpoint served stale results — at
one point returning an empty list for the repo while GraphQL showed
four releases, reproduced with anonymous curl — so both publishers
concluded no release existed and created two more. Any fix that
leaves electron-builder reading that endpoint inherits both failure
modes.

## Rejected alternatives

- **Pre-create the draft and keep `--publish always`** — the first
  attempt at this decision; disproven by the v0.1.2 run above. The
  find-existing path depends on the same stale REST list endpoint,
  so the race survives.
- **Upgrade electron-builder and hope the race is fixed upstream** —
  the concurrent create in its GitHub publisher is long-standing,
  and no upgrade changes GitHub's list-endpoint staleness. An
  upgrade can still happen independently.
- **Serialize the publish step** (sequential electron-builder
  invocations per target) — doubles universal packaging time and
  still list-then-creates against the stale endpoint; serializing
  removes the TOCTOU race but not the stale-read duplicate.
- **Retry/poll until the pre-created draft is visible before
  publishing** — CI's own read proving visibility says nothing
  about the freshness of the list electron-builder's request gets
  served seconds later.

## Rationale

The feed metadata is still generated by the same tool that built the
artifacts — latest-mac.yml and the blockmaps come out of
electron-builder's build, so [[DEC-028]]'s no-drift property holds;
CI only moves files. Creation happens exactly once, serially, before
any concurrency exists, and uploads target the release by tag —
by-tag reads were consistent throughout the incident that broke the
list endpoint. The GraphQL assertion turns any regression — a future
duplicate, a partial upload — into a red run instead of a silently
split update feed, which is the failure [[DEC-029]]'s static-feed
posture can least afford.
